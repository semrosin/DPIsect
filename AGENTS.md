# AGENTS.md — DPIsect

Точка входа для AI-агентов. **Обязателен к прочтению перед любой задачей.**
Краткий гид по правилам и навигации; детали — в `docs/`.

> Для людей: `[ЗАГЛУШКА: …]` — решение ещё не принято. Заполнить и удалить
> маркер до начала работы. Список заглушек: `grep -rn "ЗАГЛУШКА" .`

## Проект

DPIsect — активный пробер для исследования DPI: диагностика сбоев TLS/TCP,
поиск триггеров фильтрации и локализация сетевого вмешательства.
Язык: Go. Платформа: только Linux (Windows и macOS — не цели проекта).

## Заглушки

Пока маркер `[ЗАГЛУШКА: …]` не удалён, действует правило:

- **§Команды** — задачи, требующие сборки/тестов, не выполняются,
  пока команды не заданы; fallback-команды из §Команды — только с
  явной пометкой «не проектные».
- **Стратегия слияния PR** (`GIT_WORKFLOW.md` §5) — PR не создаются;
  результат остаётся в ветке и фиксируется в отчёте.
- **Do Not Scan** (`SAFETY.md` §1) — пока файла нет, любая серия по
  `target` требует явного подтверждения пользователя.

## Принципы

- Матрица — каталог вопросов, а не результаты измерений. Приоритет P0
  не включает вопрос в первый релиз автоматически.
- **Фильтр по `question_id`:** при работе над задачей этапа N берите
  только ID, перечисленные в `docs/DEVELOPMENT.md` §Этап N (блок
  «Обязательно»); остальные строки `RESEARCH_MATRIX.md` — справочный
  каталог, не scope. ID из «Не входит в этап» — не добавлять без
  явного решения пользователя.
- Различайте наблюдение, гипотезу о механизме и атрибуцию классу устройств.
- `valid-session` и `raw-experiment` — разные режимы с разными критериями
  успеха.
- Результат `helper` не переносится на маршрут `target` автоматически.
- Если требования или решения не определены и не выводятся из проекта —
  спросите пользователя, не выдумывайте.

## Границы

**Всегда**
- Сохранять чужие изменения; проверять `git status` перед работой.
- Обновлять документацию вместе с изменением поведения; удалять устаревшее.
- Указывать `question_id` в экспериментальных изменениях (формат — в
  `docs/GIT_WORKFLOW.md`).

**Ситуация → решение**

| Ситуация | Решение |
| --- | --- |
| Запуск сетевых проб вне утверждённого плана опыта | Сначала спросить (бюджет серии — `docs/EXPERIMENTS.md`) |
| Новая внешняя зависимость | Сначала спросить (`docs/GO_STYLE.md` §8) |
| Изменение границ между компонентами или публичных интерфейсов | Сначала спросить (`docs/ARCHITECTURE.md`) |
| Новая директория верхнего уровня, кроме `experiments/` | Сначала спросить (`docs/GO_STYLE.md` §8); `experiments/` разрешена |
| `push`, публикация или слияние PR без поручения | Никогда |
| Коммит напрямую в `main` | Никогда |
| `amend`, `rebase`, `force-push` без поручения | Никогда |
| Raw-пробы и невалидные TCP-поля по чужим `target` | Никогда: сначала `lab`, затем свой `helper` (`docs/SAFETY.md` §1) |
| Коммит pcap, ключей, `SSLKEYLOGFILE` и других секретов в репозиторий | Никогда (`docs/SAFETY.md` §5) |
| Удаление или перезапись чужих изменений без разрешения | Никогда |
| Выдавать гипотезы, `inconclusive` или незапущенные проверки за подтверждённые результаты | Никогда (`docs/EXPERIMENTS.md` §7) |

## Git

Ветки, коммиты и PR — `docs/GIT_WORKFLOW.md`. Формат описания PR —
`.github/pull_request_template.md` (если файл существует).

Если в задаче создана ветка, последним шагом выдайте на русском: имя ветки,
заголовок и описание PR. Подготовка текста PR не означает его публикацию.

## Критерии готовности

- [ ] Изменение атомарно и соответствует задаче.
- [ ] Тесты добавлены или указана причина их отсутствия.
- [ ] Выполнены проверки из раздела «Команды»; результаты и невыполненные
      проверки перечислены отдельно.
- [ ] Для эксперимента: результат записан со статусом `confirmed` /
      `refuted` / `inconclusive` и ссылкой на артефакты в
      `experiments/<experiment_id>/`.
- [ ] Документация актуальна.
- [ ] Текст PR подготовлен (если создана ветка).
