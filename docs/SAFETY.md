# Безопасность сетевых проб

Правила допустимых целей, лимитов, привилегий и обращения с данными.
Документ отвечает на вопрос «можно ли это делать», а не «как это делать».
Методология — в `EXPERIMENTS.md`; необратимые запреты — в `AGENTS.md`.

**Этот документ не заменяет юридическую консультацию и институциональный
этический обзор.** Перед первой серией проб в новой сети или стране —
уточнить применимое законодательство и условия провайдера.

## 1. Классификация целей

Чем «страннее» пакет, тем более «своей» должна быть цель.

| Цель | `valid-session` | Raw-проба / невалидные TCP-поля |
| --- | --- | --- |
| `lab` (изолированный стенд) | Разрешено | **Разрешено** |
| `helper` (свой сервер) | Разрешено | **Разрешено**, с лимитами (§3) |
| `target` (чужой сайт) | **Разрешено** | **Запрещено** |

- Raw-пробы, невалидные TCP-поля, конфликтующие потоки — только `lab`,
  затем `helper`. Никогда — по чужому `target`.
- Для чужого `target` — только обычные подключения, как браузер.
- Для обычных `valid-session` по решению пользователя предварительные
  серии в `lab` и на `helper` не обязательны. Доступность сети не
  предполагается доказанной: недостающие наблюдения ограничивают вывод.
  Для raw-проб сохраняется последовательность: сначала `lab`, затем свой
  `helper`; raw-пробы по чужим `target` запрещены.
- **Do Not Scan.** Вести список хостов/сетей, по которым запрещены
  любые пробы. При жалобе — добавить немедленно, без обсуждения.
  Проверять список перед каждым планом опыта. Хранение —
  `docs/DO_NOT_SCAN.md`: `[ЗАГЛУШКА: создать файл — задача пользователя,
  список может быть пустым]`. Пока файла нет: любая серия по `target`
  требует явного подтверждения пользователя, а факт жалобы и
  добавления фиксируется в журнале серии (§5, «Аудит»), чтобы запись
  не потерялась.

## 2. Правовые ограничения

- Активные измерения в некоторых юрисдикциях могут рассматриваться как
  нарушение закона или ToS провайдера. Уточнять до первой серии.
- Собственность на инфраструктуру: только `lab`, `helper` и обычные
  подключения к `target`.
- Результаты исследования не являются основанием для атакующих действий
  по чужим системам.
- Общая инфраструктура: за CGNAT один внешний адрес обслуживает многих
  абонентов. Агрессивная серия с одного клиента может затронуть чужих —
  учитывать при бюджете и выборе времени (см. §3).

## 3. Лимиты серии

Защита от непреднамеренного DoS:

- **Бюджет** — обязательные поля в плане опыта (см. `EXPERIMENTS.md` §4,
  `budget`): `max_packets`, `max_bytes`, `max_rate_pps`,
  `max_duration_s`, `stop_conditions`. Стартовые значения, если нет
  обоснования иного:
  - `max_packets`: ≤ 100 на серию;
  - `max_bytes`: ≤ 100 КБ на серию;
  - `max_rate_pps`: ≤ 10 пакетов/с;
  - `max_duration_s`: ≤ 60 с на серию;
  - `stop_conditions`: приближение к лимиту, рост retransmissions,
    аномалия в канале.
- **Превышение дефолтов** допускается только с явным обоснованием в
  `planned_wire_packets` и при цели `lab`/`helper`; для `target`
  дефолты не превышаются.
- **CGNAT.** Если клиент работает из-за CGNAT, бюджет делится на всех
  абонентов за внешним адресом. При сомнении — уменьшать
  `max_rate_pps` и `max_packets`; при явных признаках общего канала —
  остановить серию.
- **Один фактор** — один изменяемый параметр за серию.
- **Мониторинг** — следить за потреблением; при приближении к лимиту
  остановиться.
- **Запрет на «шторм»** — никаких циклов «пока не получим ответ»,
  никаких брутфорс-подобных последовательностей.
- **Kill switch.** Перед запуском определить, как остановить серию:
  сигнал процессу (`SIGINT`), таймаут, отдельный стоп-файл. Отсутствие
  способа остановить — блокер для запуска.
- **Временное окно.** Для проб по чужим `target` — по возможности
  низкая нагрузка (не пик); для `helper`/`lab` — любое, если сеть
  изолирована.

## 4. Привилегии

- **Наименьшие привилегии.** `CAP_NET_RAW` — только тому процессу, которому
  он нужен (`setcap cap_net_raw+ep` на конкретный бинарь). Не запускать
  весь бинарник от root.
- **Отсутствие эскалации.** Не комбинировать `CAP_NET_RAW` с другими
  опасными возможностями.
- **Тесты с привилегиями** — под build-тегом `privileged`
  (см. `GO_STYLE.md` §5); `go test ./...` без привилегий не должен
  падать.

## 5. Обработка данных

- **Минимизация.** Собирать только пакеты, нужные для гипотезы. Не писать
  «весь трафик на всякий случай».
- **PCAP вне git.** Сырые PCAP — в `artifacts/<experiment_id>/`
  (в `.gitignore`) или внешнем хранилище; в репозиторий — только
  метаданные, план, отчёт и `sha256` (см. `EXPERIMENTS.md` §5).
  Исключение — синтетические эталонные fixtures в `testdata/`: они
  порождаются кодом тестов, сетевого трафика не содержат и входят в git
  (`testdata/README.md`, `GO_STYLE.md` §6).
- **Права на файлы.** Сырые `*.pcap*`, `SSLKEYLOGFILE`, ключи — права
  `0600`; каталог `artifacts/` — `0700`.
- **Чувствительность.** Даже «свой» PCAP может содержать фоновый трафик и
  метаданные сторонних. Считать потенциально чувствительным.
- **`SSLKEYLOGFILE` и ключи:**
  - никогда не коммитить в git;
  - не включать логирование ключей в production-сборках; только в
    отладочных, для своих тестовых TLS-сессий;
  - файлы ключей — с правами `0600`; удалять после опыта, если больше
    не нужны;
  - `*.pcap*`, `*.key`, `SSLKEYLOGFILE` — в `.gitignore`.
- **Хранение и удаление.** PCAP и сырые логи хранятся, пока нужны для
  проверки отчёта и воспроизводимости (`H07`). Срок по умолчанию — 90
  дней, отсчитываемых от завершения этапа или публикации отчёта, а не
  от даты опыта. Продление — явное решение с указанием причины в
  отчёте; сокращение — допустимо, если отчёт уже проверен.
- **Аудит.** Для каждой серии — запись в журнале: время UTC, оператор,
  `experiment_id`, цель, бюджет, фактические показатели. Отдельно —
  записи о жалобах и добавлениях в `Do Not Scan` (пока файла нет, это
  единственный след). Это часть воспроизводимости (`H07`) и защиты
  при разборе инцидента.
- **Анонимизация.** Если планируется публикация датасета — рассмотреть
  маскирование IP и других идентификаторов.

## 6. Изолированная среда

- **По умолчанию** — отдельная сетевая namespace или контейнер с
  минимальными привилегиями.
- **Сеть** — не подключать тестовый стенд к production-сети; `veth` или
  отдельный физический сегмент.
- **Очистка** — после серии удалять временные файлы, ключи, дампы, если
  они не являются частью отчёта.

## 7. Responsible disclosure

При обнаружении уязвимости в чужой инфраструктуре (не просто DPI-блокировка,
а, например, ошибка в сервере или маршрутизаторе): сообщить владельцу,
дать время на исправление, не публиковать эксплойт до согласованной даты.

Контакт для disclosure пока не зафиксирован. **До первой серии по чужим
`target`** контакт должен быть определён; если его нет — серия по чужим
`target` не начинается. При обнаружении уязвимости — остановиться и
уточнить у пользователя, кому и как сообщать.

## 8. Чек-лист перед первой сетевой пробой

- [ ] Цель — `lab`, `helper` или `target`? Для `target` — только обычные
      подключения; предварительные `lab` и `helper` для них необязательны.
- [ ] Для raw-проб: цель — `lab` или `helper`?
- [ ] Проверен `Do Not Scan` (`docs/DO_NOT_SCAN.md`)? Пока файла нет —
      получено явное подтверждение пользователя на серию по `target`.
- [ ] Определён бюджет серии (пакеты, байты, скорость, длительность,
      `stop_conditions`)? Превышение дефолтов обосновано?
- [ ] Учтён CGNAT (бюджет на всех абонентов за внешним адресом)?
- [ ] Определён kill switch (как остановить серию)?
- [ ] Привилегии минимальны (`CAP_NET_RAW` только нужному процессу)?
- [ ] План хранения PCAP/ключей: вне git, с правами `0600`, с `sha256`
      в отчёте, срок хранения отсчитывается от завершения этапа?
- [ ] Среда изолирована или есть подтверждение, что это безопасно?
- [ ] Для первой серии в новой сети — проверено применимое
      законодательство?
- [ ] Для первой серии по чужим `target` — определён контакт для
      disclosure?
