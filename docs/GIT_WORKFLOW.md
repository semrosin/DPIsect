# Работа с Git

Процесс ветвления, коммитов и PR. Необратимые запреты (`push`, коммит в `main`,
`amend`/`rebase`/`force-push`) — в `AGENTS.md` §Границы; здесь — как работать
в рамках этих границ.

## 1. Стратегия веток

`main` — стабильная и запускаемая ветка. Вся работа ведётся в короткоживущих
ветках, создаваемых от актуальной `main`; при необходимости — от другой
подходящей базы, с уточнением у пользователя. Ветка создаётся под одну задачу
и удаляется после слияния. Прямые коммиты в `main` запрещены.

Перед началом проверьте текущую ветку и состояние дерева (`git status`). Если
текущая ветка подходит для задачи — продолжайте в ней; иначе создайте новую.

Если `main` ушла вперёд за время работы — добавьте merge `main` в ветку и
разрешите конфликты. `rebase` запрещён без прямого поручения (`AGENTS.md`
§Границы); не переписывайте уже запушенную историю.

### Заброшенные ветки

Ветка, которая не была слита и больше не нужна (например, экспериментальная
ветка после отрицательного результата, если результат решено не сливать, или
ветка с отвергнутой гипотезой), удаляется только по согласованию с
пользователем. Перед удалением убедитесь, что результат зафиксирован в
`experiments/<experiment_id>/report.md` на `main` (или в issue/PR) — иначе
ссылка на опыт теряется. Самостоятельно удалять чужие ветки запрещено.

## 2. Имена веток

Формат: `тип/краткое-описание`.

| Тип работы | Префикс ветки | Тип коммита | Пример |
| --- | --- | --- | --- |
| Новая функциональность | `feat/` | `feat` | `feat/sni-generator` |
| Исправление | `fix/` | `fix` | `fix/capture-timeout` |
| Только документация | `docs/` | `docs` | `docs/update-safety` |
| Инфраструктура, зависимости, конфиги | `chore/` | `chore` | `chore: add .gitignore` |
| Экспериментальные изменения | `exp/` | по смыслу; `scope` — `question_id` (§3) | `exp/b01-sni-padding` |

### Экспериментальные ветки

Для экспериментальных изменений ветка: `exp/<question_id>-<slug>` —
например, `exp/b01-sni-padding`. Общий идентификатор эксперимента
(`experiment_id`, с датой) и тег — в §3.

Отрицательный результат — часть исследования. Ветка удаляется после
слияния PR по общему правилу (§1); результат фиксируется в отчёте
`experiments/<experiment_id>/report.md` и в описании PR. Сохранять
ветку после merge — только по согласованию с пользователем.

## 3. Коммиты

### Атомарность

Один коммит — одно логическое изменение. Запрещено смешивать в одном коммите:

- исправление и рефакторинг;
- добавление теста и изменение поведения;
- форматирование и содержательную правку;
- изменения из разных задач.

Если во время работы обнаружена смежная проблема — создайте отдельную ветку
или отложите; не включайте «попутно».

### Формат сообщения

Conventional Commits: `type[(scope)]: short description`. Язык — английский,
включая заголовок и тело. Допустимые типы: `feat`, `fix`, `docs`, `test`,
`refactor`, `build`, `ci`, `chore`, `revert`. При несовместимом изменении —
`!` после типа или `BREAKING CHANGE` в теле.

Заголовок — что сделано (кратко, до 72 символов). Тело — зачем и какие
существенные ограничения; дублировать diff не нужно.

### Связь с `question_id`

Если изменение относится к вопросу из `RESEARCH_MATRIX.md`, `scope` —
`question_id` в нижнем регистре, и в футере — `Refs:`. Это правило
действует независимо от префикса ветки (`feat/`, `fix/`, `exp/`):

```text
feat(b01): add SNI padding generator

Refs: B01
```

Для инфраструктурных изменений, не привязанных к вопросу, `scope` —
компонент (`capture`, `runner`, `docs` и т.п.):

```text
fix(capture): handle missing packets
chore: add .gitignore
```

### Изменения в `RESEARCH_MATRIX.md`

`RESEARCH_MATRIX.md` — источник истины по `question_id`, методам и
ограничениям. Правки в нём — отдельный тип изменения:

- `scope: research`, например `docs(research): clarify B04 boundaries`;
- если правка относится к конкретному вопросу — добавьте `Refs: <question_id>`;
- не смешивайте правку матрицы с изменениями кода или других документов в
  одном коммите.

### Запрет массового добавления

Не используйте `git add -A` и `git add .` без проверки. Перед коммитом:

1. `git status` и `git diff --staged` — убедитесь, что в коммит попали только
   ваши изменения.
2. `git status --ignored` — убедитесь, что `artifacts/`, `*.pcap*`, ключи и
   `SSLKEYLOGFILE` не попали в индекс (см. `.gitignore`, `SAFETY.md` §5).
3. Сверьте изменённые файлы с теми, которые вы действительно правили; чужие
   или незнакомые файлы не добавляйте — уточните у пользователя.
4. Выполните проверки из `AGENTS.md` §Команды (или fallback, если команды
   не заданы). Результаты сообщите в PR.
5. Только после этого — коммит.

### Эксперименты: `experiment_id` и теги

Единое правило для всех артефактов эксперимента:

- `experiment_id` = `<question_id>-<slug>-<YYYY-MM>`, например
  `b01-sni-padding-2026-11`; используется в пути
  `experiments/<experiment_id>/` и в отчёте (`EXPERIMENTS.md` §4);
- ветка = `exp/<question_id>-<slug>` — короткая, удаляется после merge;
- тег = `exp/<experiment_id>` — постоянный.

При завершении серии опытов ставьте тег на коммит в `main`, из которого
воспроизводится конфигурация. В отчёте — тег рядом с путём к PCAP и
`sha256`: шаблон отчёта — `EXPERIMENTS.md` §4 (`artifacts`), политика
хранения PCAP — `SAFETY.md` §5.

## 4. Чужие изменения

Не удаляйте, не перезаписывайте и не переносите уже существующие изменения
без явного разрешения. Если их нельзя безопасно отделить от вашей работы —
остановитесь и уточните действия. При невозможности создать ветку или коммит
из-за ограничений среды сообщите об этом и приведите предлагаемые имя ветки
и сообщения коммитов.

## 5. Слияние и PR

Стратегия слияния PR (merge-commit / rebase / squash) **не зафиксирована**:
`[ЗАГЛУШКА: стратегия слияния — зафиксировать и обновить этот раздел]`.
До заполнения маркера — уточняйте у пользователя (правило — `AGENTS.md`
§Заглушки). Решение должно быть принято до первого PR, закрывающего
критерий выхода этапа 1; до этого момента PR не создаются, результат
остаётся в ветке и фиксируется в отчёте.
Заголовок PR — Conventional Commits на английском независимо от стратегии:
он остаётся в истории при любом варианте.

Описание PR — русский, по шаблону `.github/pull_request_template.md`.
Шаблон покрывает: что изменено, зачем (`Refs:`), выполненные проверки,
блок эксперимента (для `exp/`), критерии готовности из `AGENTS.md`
§Критерии готовности, ограничения. Если шаблон нужно изменить — правьте
файл, а не описывайте структуру здесь: единственный источник истины —
шаблон.

Создание текста PR не является публикацией. `push`, публикация и слияние —
только по прямому поручению (см. `AGENTS.md` §Границы).

## 6. Откат

Для отката используйте `git revert` — создаётся новый коммит с типом
`revert:` и футером `Refs:` на исходный коммит или `question_id`:

```text
revert: feat(b01): add SNI padding generator

This reverts commit <hash>.

Refs: B01
```

Для отката экспериментального коммита укажите в теле ссылку на
`experiments/<experiment_id>/`, если результат уже зафиксирован в отчёте.

Не откатывайте force-push’ем уже опубликованную историю (`AGENTS.md`
§Границы → Никогда).

## 7. Завершение задачи

Если в рамках задачи создана одна или несколько веток, последним шагом
выдайте для каждой: имя ветки, заголовок PR и описание на русском —
по шаблону `.github/pull_request_template.md`: что изменено, `question_id`
(если применимо), выполненные проверки с результатами, существенные
ограничения. Отметьте невыполненные проверки и их причины.

Текст PR готовится, но не публикуется: `push` и создание PR — только по
прямому поручению (`AGENTS.md` §Границы).

Если новых веток не создавалось (работа продолжена в существующей), это
требование само по себе не обязывает предлагать PR — но при наличии
изменений укажите, в какой ветке они находятся.
