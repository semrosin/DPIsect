# Работа с Git

## Ветки и чужие изменения

Перед началом проверьте текущую ветку и состояние рабочего дерева. Если текущая ветка подходит для задачи, продолжайте работу в ней. В остальных случаях создайте отдельную ветку от подходящей базы; при неясности базы или назначения ветки уточните у пользователя. Используйте префикс по назначению и краткое название через дефис: `feature/…`, `fix/…` или `docs/…`.

Учитывайте уже существующие изменения: не удаляйте, не перезаписывайте, не переносите и не включайте чужие изменения в коммит без явного разрешения. Если их нельзя безопасно отделить от своей работы, остановитесь и уточните дальнейшие действия. При невозможности создать ветку или коммит из-за ограничений среды сообщите об этом и приведите предлагаемые название ветки и сообщения коммитов.

## Коммиты

Создавайте коммиты самостоятельно по завершённым логическим изменениям задачи, если пользователь не потребовал обратного. Каждый коммит должен быть атомарным: содержать одно связное изменение вместе с необходимыми для него проверками и документацией и оставлять проект в согласованном состоянии. Не смешивайте несвязанные изменения ради одного коммита. Перед коммитом проверьте состав staged-изменений и выполните подходящие проверки; если проверка недоступна, сообщите об этом.

Пишите сообщения коммитов на английском языке, включая заголовок и, при наличии, тело. Используйте Conventional Commits: `type[(scope)]: short description`. Например, `feat: add experiment configuration`, `fix(capture): handle missing packets`, `docs: describe experiment methodology`. Допустимы стандартные типы, в том числе `feat`, `fix`, `docs`, `test`, `refactor`, `build`, `ci` и `chore`; при несовместимом изменении используйте `!` или отметку `BREAKING CHANGE` в теле. Сообщение должно отражать фактическое изменение.

## Результат работы

Если агент создал одну или несколько веток в рамках задачи, последним шагом он выдаёт для каждой ветки её имя, название PR и описание PR на русском. Описание объясняет проблему и изменение, приводит выполненные проверки с результатами и существенные ограничения. Отметьте невыполненные проверки и их причины. Если ветка уже существовала и новых веток не создавалось, это требование само по себе не обязывает предлагать PR.

Создание текста PR не является публикацией PR. Не выполняйте push, публикацию или слияние без соответствующего поручения.
