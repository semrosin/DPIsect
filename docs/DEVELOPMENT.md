## Этап 1. Основа

**Цель:** работают генератор проб и две точки capture; классификатор
различает известные причины на управляемых примерах; есть базовые
контроли DNS и TCP-доступности.

**Зависит от:** ничего (фундамент). Этап включает создание
инфраструктуры: клиент в исследуемой сети, `helper`, `lab` с
управляемыми drop/reorder/delay/MTU и независимая контрольная точка.
По решению пользователя этап 1 может закрываться с локальным `helper`
без удалённого сервера; два захвата на одном интерфейсе подтверждают
только локальную работу компонентов, а не наблюдение двух концов сети.
Без контрольной сети `A01` может закрыться как `inconclusive` — это
допустимо, но фиксируется явно.

**Обязательно:** `A01`, `A02`, `A03`, `A04`, `A07`, `H01`, `H02`, `H03`,
`H04`, `H07`, `G01`, `G02`.

**Не входит в этап:** `A05`, `A06` — после пилота или вне v1; см.
«Вне scope v1» и `RESEARCH_MATRIX.md`.

### Подшаги этапа 1

1. Скелет репозитория: `cmd/`, `internal/`, `testdata/`; `go.mod` с
   зафиксированной версией Go (`GO_STYLE.md` §1).
2. Заполнить `AGENTS.md` §Команды (сборка, тесты, линтер, версия Go);
   удалить fallback-абзац.
3. `ARCHITECTURE.md`: роли и границы generator / runner / capture /
   helper / analyzer; интерфейсы между ними; граница `valid-session` vs
   `raw-experiment` в коде.
4. Генератор проб: `valid-session` и `raw-experiment` как разные пути
   (`GO_STYLE.md` §4).
5. Две точки capture: клиент и `helper`; сохранение PCAP вне git
   (`SAFETY.md` §5).
6. `helper`-заглушка: принимает соединения, логирует серверные события
   (`A07`, `H07`).
7. `lab`-заглушка: минимальный набор drop/reorder/delay/MTU для `H01`,
   `H02`; без этого классификатор не на чем проверить.
8. Fixture с известными причинами (`drop`, `rst_injection`, `tls_alert`,
   `throttling`) в `testdata/` + классификатор; разметка и границы
   применимости — рядом с fixture (`GO_STYLE.md` §6, `H01`).
9. Первый полный опыт на одном контрольном профиле — с артефактами в
   `experiments/<experiment_id>/` (`EXPERIMENTS.md` §4).

**Критерии выхода** (в скобках — артефакт, подтверждающий выполнение):

- [ ] Генератор и два capture работают на управляемом примере.
      (отчёт `experiments/<experiment_id>/report.md` + PCAP вне git,
      `SAFETY.md` §5)
- [ ] Классификатор различает полный набор `H01` на fixture: отсутствие
      вмешательства, `drop`, `rst_injection`, модификация, TLS Alert,
      throttling. Промежуточно допустимо `drop` + `rst_injection` —
      как явно отмеченное ограничение, не как «готово».
      (fixtures в `testdata/` + результаты классификации в отчёте)
- [ ] Контрольный профиль и `helper` принимают пробы.
      (helper log + client PCAP в `experiments/<experiment_id>/`)
- [ ] Для одного контрольного профиля сохранён полный набор артефактов
      в `experiments/<experiment_id>/` (PCAP — вне git, см.
      `SAFETY.md` §5; шаблон отчёта — `EXPERIMENTS.md` §4).
      (каталог `experiments/<experiment_id>/` с `report.md` по шаблону)
- [ ] `ARCHITECTURE.md` заполнен (не заглушка): роли и границы
      компонентов (generator / runner / capture / helper / analyzer)
      зафиксированы. (`docs/ARCHITECTURE.md`)
- [ ] Все заглушки в `AGENTS.md` §Команды заполнены или явно помечены
      как неприменимые до появления кода. (`AGENTS.md` §Команды)

с этим способом финализации ещё не проведён; исходные метаданные

## Этап 2. Причинный SNI-эксперимент

**Цель:** установить, есть ли воспроизводимый SNI-эффект, и какие
объяснения он исключает.

**Зависит от:** этап 1 (генератор, классификатор, capture).

**Обязательно:** `B01`, `B02`, `B04`, `B07`.

**Не входит в этап:** `B03`, `B05`, `B06`, `B08` — P1, после пилота.

**Критерии выхода:**

- [ ] Для каждого обязательного вопроса создан отчёт в
      `experiments/<experiment_id>/` со статусом `confirmed`, `refuted`
      или `inconclusive`. (`experiments/<experiment_id>/report.md`,
      `EXPERIMENTS.md` §4)
- [ ] Как минимум один вопрос имеет статус `confirmed` либо все —
      `refuted`/`inconclusive` с описанной причиной.
      (front-matter отчётов)
- [ ] Зафиксировано, какие альтернативные объяснения исключены.
      (секция `results.excluded_hypotheses` в отчётах)

**Если эффект не подтверждён:** см. таблицу «Исход этапа 2» ниже —
этап всё равно закрывается; отрицательный исход валиден
(`EXPERIMENTS.md` §7).

### Исход этапа 2 → дальнейшие этапы

| Исход этапа 2 | Этап 3 | Этап 4 | Этап 5 |
| --- | --- | --- | --- |
| `confirmed` | по плану: `C01`, `C03` | не блокируется (зависит только от этапа 1) | `E04`, `E05` + `F01–F04` |
| `refuted` или `inconclusive` | N/A: другой триггер или N/A; решение фиксируется в отчёте | не блокируется | При отсутствии другого воспроизводимого триггера — `E04`/`E05` как `inconclusive`, `F01–F04` не выполняются |

Отрицательный результат не блокирует этапы 1 и 4.

**Обязательно:** `C01`, `C03`.

**Критерии выхода:**

## Этап 4. Пакетные преобразования

**Цель:** проверить реакцию наблюдателя на поддельные пробы с независимым
изменением полей и валидацией endpoint.

**Зависит от:** этап 1 (генератор, capture). Может идти параллельно с
этапами 2–3.

**Обязательно:** `D01`, `D02`, `D03`, `D04` — каждое поле (`TTL`, `SEQ`,
`ACK`, `checksum`) меняется отдельно.

**Не входит в этап:** `D05`–`D09` — после пилота.

**Критерии выхода:**

- [ ] Отчёты по обязательным вопросам созданы.
      (`experiments/<experiment_id>/report.md`)
- [ ] Для каждой пробы подтверждено фактическое поведение endpoint
      (принято / отвергнуто). (секция `actual_wire_validation` +
      `observations` отчётов)

## Этап 5. Состояние и локализация

**Цель:** определить область и время остаточного эффекта; для
подтверждённого эффекта — оценить TTL-границу.

**Зависит от:** этап 1; для `E04` и `E05` нужен воспроизводимый
триггер, для `F01–F04` — подтверждённый эффект. Результаты этапа 2
помогают установить эти предпосылки.

**Обязательно:** `E04`, `E05`.

**Не входит в этап:** `F01–F04` — только для подтверждённого эффекта;
`E01`, `E02`, `E06`, `E07`, `F05`, `F06` — при необходимости, P1/P2.

**Критерии выхода:**

- [ ] Отчёты по `E04`, `E05` созданы. Без воспроизводимого триггера
      оба результата — `inconclusive` с указанием причины; область и
      время остаточного эффекта не оцениваются. Если после воспроизводимого
      триггера остаточный эффект не обнаружен, время его исчезновения
      (`E05`) не оценивается: результат — `inconclusive` с причиной.
      (`experiments/<experiment_id>/report.md`)
- [ ] Для подтверждённого эффекта зафиксирована TTL-граница с оговорками
      (`F01–F04`); при отсутствии индикатора — результат `inconclusive`.
      (отчёты `F01`–`F04`; при отсутствии — явная отметка в отчёте `E04`/`E05`)
- [ ] Если эффект не подтверждён — `F01–F04` не выполняются; это
      зафиксировано в статусе этапа. (статус в таблице §Статус + отчёт `E04`)

## Вне scope v1

Перечисленное не входит в первую версию, даже если присутствует в матрице:

- `A05` (продолжение передачи после RST), `A06` (throttling, порог
  байтов) — только после пилота.
- `G03` (IPv6), `G04` (QUIC), `G05` (ECH), `G06` (HTTP) — после v1.
- `G07`, `G08`, `H05`, `H06` — P1/P2, по результатам пилота.
- Одновременное включение QUIC, ECH, IPv6 и HTTP «ради охвата» запрещено.

## Семантика `question_id`

Префикс обозначает класс вопроса; сами ID и их описания — в
`RESEARCH_MATRIX.md`. Синтаксис в Git (`feat(b01):`, `Refs: B01`,
`experiments/<experiment_id>/`) — в `GIT_WORKFLOW.md` §3.

| Префикс | Класс вопросов |
| --- | --- |
| `A` | Симптомы и механизм вмешательства |
| `B` | Признак, запускающий вмешательство (SNI и условия) |
| `C` | Сегментация, порядок и сборка потока |
| `D` | Поддельные пробы и расхождение интерпретаций |
| `E` | Состояние, направление и остаточный эффект |
| `F` | Локализация (TTL) |
| `G` | Границы покрытия и альтернативные причины |
| `H` | Корректность, проверка гипотез и воспроизводимость |
