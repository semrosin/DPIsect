# Go Style — DPIsect

Baseline: [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments),
[Google Go Style Guide](https://google.github.io/styleguide/go/),
[Uber Go Style Guide](https://github.com/uber-go/guide);
[Effective Go](https://go.dev/doc/effective_go) — справочно.

Здесь — только уточнения для DPIsect: сетевое программирование,
привилегии, платформенные ограничения, воспроизводимость экспериментов.
Общие правила из baseline не дублируются.

## 1. Форматирование и статические проверки

- `gofmt` / `goimports` — обязательны, без исключений.
- `go vet ./...` — без замечаний. Для сетевого кода `vet` особенно важен:
  ловит утечки `context` и подозрительные конкурентные паттерны.
- `go mod tidy` — перед коммитом, если менялись импорты или `go.mod`.
- `golangci-lint run` — когда появится конфиг (`.golangci.yml`);
  до этого не блокирует коммит (см. `AGENTS.md` §Команды).
- После изменения любого `.go`-файла — прогон `gofmt -s -w` и `go vet ./...`
  до коммита.
- Версия Go фиксируется в `go.mod` (`go 1.x.y`); не использовать
  экспериментальные языковые возможности без явной необходимости.

## 2. Ошибки

- Ошибка — последнее возвращаемое значение; проверка — сразу после вызова.
- Не игнорировать `err` без обоснования в комментарии. `_ = f()` допустим
  только если ошибка действительно не влияет на результат — и это
  объяснено рядом.
- Оборачивание с контекстом: `fmt.Errorf("…: %w", err)`. Сравнение —
  `errors.Is` / `errors.As`, не сравнение строк.
- Несколько ошибок сразу — `errors.Join` (Go 1.20+). В тексте ошибки
  не должно быть цепочки «failed: failed: failed».
- `panic` — только для ошибок программиста (нарушенный инвариант) или
  невозможности инициализации. Не для рабочих путей, не для «на всякий
  случай».
- `os.Exit` / `log.Fatal` — только в `main`. В библиотечном коде —
  возврат `error`.
- Для DPIsect: ошибки capture, парсинга пакетов и таймаутов должны быть
  видимы и обёрнуты, иначе классификатор даст `inconclusive` по
  технической причине, а не по результату опыта.

## 3. Context и горутины

- `context.Context` — первым параметром; не хранить в структурах.
- Все сетевые операции — с дедлайном или отменой. `defer cancel()`
  обязателен, иначе утечка таймера.
- У каждой горутины есть владелец и условие остановки. Проверка — через
  `ctx.Done()`, `errgroup` или явный `done`-канал.
- `time.Sleep` как синхронизация сетевых событий запрещён. Альтернативы:
  каналы, `time.Timer`/`time.Ticker`, события capture. Задержка между
  пакетами — только как явный параметр опыта в плане пакетов.
- Горутина, которая может паниковать (парсинг пакетов, пользовательский
  ввод), оборачивается `recover` с логированием и передачей ошибки
  владельцу через канал/`errgroup`; «тихая» паника недопустима.
- `net.Conn` deadlines сбрасываются перед каждой операцией, если она
  может занимать разное время; не выставлять дедлайн «на всю жизнь»
  соединения.
- Код с горутинами проверяется `go test -race ./...` в CI и перед
  коммитом, если изменение касается конкурентности.

## 4. Сеть и raw-сокеты

- Явные таймауты на `Dial`, `Read`, `Write`, TLS-handshake — не полагаться
  на системные дефолты.
- Чтение потока — с ограничением: `io.LimitReader`, `io.CopyN`,
  `bufio.Scanner.Buffer` с максимальным размером строки. Не допускать
  неограниченного роста буфера из сети.
- `valid-session` и `raw-experiment` — разные пути в коде: разные типы
  возвращаемых результатов, разные критерии ошибок, разные тесты.
- Raw-сокеты и невалидные TCP-поля — только в коде, который по построению
  не может быть запущен по чужому `target` без явного флага и
  подтверждения. Это правило согласовано с `AGENTS.md` §Границы и
  `SAFETY.md`.
- Запись PCAP и логирование не блокируют сетевой цикл: буферизация и
  отдельная горутина с владельцем и условием остановки.

## 5. Привилегии и платформа

- Платформенный код — `//go:build linux` (современный синтаксис; не
  `// +build`) или суффикс `_linux.go`. Не-Linux-пути не поддерживаются;
  не выдавать непроверенную совместимость за реализованную.
- Тесты, требующие `CAP_NET_RAW` / `CAP_NET_ADMIN`, — под build-тегом
  `privileged`. `go test ./...` без привилегий не должен падать.
- Проверять, что оба режима компилируются: с тегом и без
  (`go build ./...` и `go build -tags privileged ./...`).

## 6. Тестирование

- Табличные тесты; каждый кейс — `t.Run("name", ...)`. Для
  экспериментальных проверок имя подтеста начинается с `question_id`
  (например, `TestB01_SNIPadding`).
- `t.Helper()` — в helper-функциях, чтобы ошибки указывали на вызывающий
  тест, а не на helper.
- `t.Cleanup(fn)` — для освобождения ресурсов; `t.TempDir()` — для
  временных файлов. Не оставлять файлы в `/tmp` после тестов.
- `t.Parallel()` — для независимых unit-тестов; не для тестов,
  использующих общий сетевой ресурс или привилегии.
- Unit-тесты — быстрые, без сети и без привилегий.
- Интеграционные и привилегированные тесты — под build-тегом
  `privileged`; запуск отдельной командой.
- Fixtures с известными причинами (`drop`, `rst_injection`,
  `tls_alert`, `throttling`) — эталонные трассы в `testdata/`, на них
  проверяется классификатор. Разметка и границы применимости — рядом
  с fixture. Fixtures в git (исключение `!testdata/**/*.pcap` в
  `.gitignore`); сырые артефакты опытов — вне git (`SAFETY.md` §5).
- Для воспроизводимости — `go test -count=1 ./...` при проверке
  изменений поведения (не полагаться на кэш результатов).
- `go test -race ./...` — перед push, если изменение касается
  конкурентности.

## 7. Логирование и документация кода

- Логи — `log/slog` (structured). Ключи короткие и стабильные: `event`,
  `flow`, `dst_ip`, `dst_port`, `sni`, `error`. Уровни: `Debug` — для
  диагностики, `Info` — события опыта, `Warn` — восстановимые аномалии,
  `Error` — требует вмешательства.
- Не логировать секреты: `SSLKEYLOGFILE`, содержимое ключей, payload
  приватных сессий (см. `SAFETY.md` §5).
- Пакетный комментарий — `// Package <name> …` перед `package`.
- Комментарий экспортируемого идентификатора начинается с его имени:
  `// HandleProbe обрабатывает …`.
- Документировать поведение, граничные случаи, ошибки и неочевидные
  инварианты — а не пересказывать код.
- Язык — английский (см. `AGENTS.md` §Языки).
- TODO — с ссылкой на issue или владельца: `// TODO(#123): …` или
  `// TODO(username): …`. Без owner/issue TODO не принимается.

## 8. Структура и зависимости

Структура каталогов:

- `cmd/<binary>/` — точки входа; имя бинаря — одно слово (`dpi-prober`,
  `dpi-runner`), не `main`;
- `internal/` — внутренние пакеты, не публикуемый API (по умолчанию —
  сюда);
- `pkg/` — публикуемые пакеты; **не создавать без внешних потребителей**
  (Google Style рекомендует `internal/` по умолчанию);
- `testdata/` — fixtures и эталонные трассы;
- `experiments/` — планы, отчёты и метаданные опытов (корень
  репозитория, в git);
- `artifacts/` — сырые PCAP и логи опытов, вне git (политика —
  `SAFETY.md` §5; структура — `EXPERIMENTS.md` §5).

Внешние зависимости:

- Стандартная библиотека в приоритете.
- Новая зависимость — «Сначала спросить» (`AGENTS.md` §Границы).
- Критерии допуска: активная поддержка, приемлемая лицензия, отсутствие
  cgo (если не требуется для задачи), разумный размер.
- Фиксированная версия в `go.mod`; обоснование выбора — в PR.

Секреты и конфигурация:

- Не хранить в коде и в git: ключи, `SSLKEYLOGFILE`, токены.
- Конфиги экспериментов — в `experiments/<experiment_id>/` или в `docs/`
  (если это шаблон, а не результат); шаблон — `docs/config.example.yaml`.
- `*.pcap*`, `*.key`, `SSLKEYLOGFILE` — в `.gitignore`.

Версионирование бинаря:

- Версия и commit — через
  `-ldflags "-X main.version=… -X main.commit=…"` при сборке; выводить
  в `--version` и в логи старта (нужно для `H07`).
